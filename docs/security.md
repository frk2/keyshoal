# Keyshoal security and peer replication

Keyshoal protects a closed vault copied from disk and authenticates data exchanged on an untrusted LAN. It does not protect secrets from a compromised operating system, browser, or unlocked app. The application and protocol have not been independently audited.

## Two secrets and per-record encryption

- A system CSPRNG generates the 32-byte security key, 16-byte vault ID and 16-byte KDF salt. Linux does not persist the security key. iOS stores it in the current device’s unlocked-only Keychain. No device saves the passphrase.
- Compute `HMAC-SHA-256(key=security key, message=exact UTF-8 passphrase)`. Stretch the result with Argon2id v1.3 using 64 MiB, 3 passes, 4 lanes and a 32-byte result. Fixed format parameters prevent a hostile header from asking for arbitrary KDF resources. HKDF-SHA-256 with the vault ID as salt and `keyshoal/v1/{catalogue,password,file,journal,transport}` as distinct context strings derives separate keys.
- One login has separate catalogue and password XChaCha20-Poly1305 boxes. Each uses a fresh random 24-byte nonce and authenticates a context label, vault ID, and record ID. The catalogue contains the title, canonical website origin and username. The password is a distinct encrypted string. Listing, network synchronization, merging, and conflict detection never open a password box. A password is opened only for the user’s explicit reveal, edit, copy, or selected exact-origin autofill.
- Scope and limits remain important. Managed runtimes do not guarantee byte or string erasure from memory. OS clipboard managers, accessibility, memory dumps and screenshots are different trust boundaries. Keep both factors and an offline copy of the encrypted journal.

The primitives come from [noble-hashes](https://github.com/paulmillr/noble-hashes) and [noble-ciphers](https://github.com/paulmillr/noble-ciphers). Argon2id follows the memory-constrained profile in [RFC 9106](https://www.rfc-editor.org/rfc/rfc9106#section-4).

## Full replicas and the change graph

Each device durably stores the complete local journal, not just an index or a cache of selected passwords. A newly joined device receives the journal when it first meets any existing replica. No leader tracks a sequence, receipt, authoritative snapshot or primary address. Devices can create, edit, delete, and resolve already-known conflicts without another node.

A replica starts with `KSREPL02`, followed by the 76-byte authenticated empty v1 vault header, a packed change list, and a 32-byte HMAC-SHA-256 over everything that precedes it under the journal key and store context. Integers use unsigned big-endian order. The list begins with a 32-bit count. Each entry is a 32-bit length and a change block. Entries are sorted by their 32-byte SHA-256 IDs.

A change block contains the 16-byte login ID, 16-bit parent count, 32-bit encrypted box length, sorted 32-byte parent IDs, a sealed one-record v1 snapshot (empty for a deletion), and a 32-byte HMAC under the journal key and event context. The ID hashes the entire authenticated block. The v1 snapshot binds its encrypted record to the same vault and login. All parents must exist in the merged set and belong to that login. A record’s current versions are the graph heads. Edits to separate records commute. Two unseen edits of the same record produce two heads. Edit-versus-delete also produces a conflict. Resolving a conflict references **all** reviewed heads and reuses the selected encrypted box or tombstone. Choosing the same result with the same heads produces the same operation. An unseen late edit, or two contrary offline resolutions, can legitimately open a new conflict. Autofill will not guess among conflicting passwords.

All platforms persist the encrypted journal atomically. Linux uses private directories and 0600 data files. Windows uses a protected, current-user and SYSTEM NTFS ACL under Local AppData. iOS uses an atomic protected file excluded from backup and the vault key in Keychain. The preview allows 8 MiB and 8,192 events per vault. It does not compact history or securely erase deleted or superseded ciphertext. Deletion removes a login from the active vault and propagates a tombstone. Historical password boxes stay encrypted for replication. An attacker able to replace files with a previously authentic journal can cause a rollback; rollback-resistant hardware state is not implemented.

## Setup, Bonjour, and missing-block exchange

A QR or setup code transfers the security key and authenticated empty header, never the passphrase or password records. It does not grant vault access without the passphrase. It works without the source online and with any existing replica, rather than enrolling the device with a master. Nothing in the code expires on the network. Dismissing or timing out the displayed QR is only a screen privacy measure. A copied setup code is as sensitive as the security key. In this preview all devices holding the vault factors are members of the same cryptographic trust group. Per-device revocation and recovery from group credential compromise require a new vault and password rotation.

- Peers advertise and browse `_keyshoal-v2._tcp.local.` using Bonjour/mDNS and random per-session service names. No vault ID, login data, or key is advertised. Discovery is a hint, not peer authentication. An unrelated or unauthenticated peer does not count toward the sync indicator. There is no cloud, forwarding, or global discovery service.
- An unlocked peer listens for length-prefixed TCP inventories. The requester sends the sorted hashes it already holds, sealed with XChaCha20-Poly1305 under the transport key in the inventory context. The responder sends only missing binary blocks plus a digest of its current inventory, in a separate authenticated reply context that binds the response to the exact encrypted request. A new random nonce is used every time. Requests cannot mutate the responder’s disk state. Replaying an old request can at most obtain an encrypted reply bound to that old request. Repeating a valid block when merging is idempotent.
- This is rsync-style missing-block exchange using content hashes, not the rsync wire protocol or a rolling checksum over whole files. Both directions use exactly the same inventory-and-pull procedure, so one peer can catch up with another that never knew the original device. The status shows the last observed matching inventory for reachable authenticated peers, not a guarantee about absent peers.
- Wire authentication is vault-group authentication, not separate device identities. The transport is encrypted with the unlocked vault’s symmetric key. It does not use TLS and does not provide forward secrecy against later disclosure of vault factors and a capture of the traffic. Discovery and transport can leak presence, timing and size. DoS, malicious group members, local network isolation and compromised devices are outside the preview’s guarantees. Sync stops on lock or pause, and on iOS when the app goes into the background.

## Chrome boundary

The Manifest V3 extension uses `activeTab`, `scripting` and `nativeMessaging` with no broad host permission or persistent browser password cache. Chrome permits only the ID in the locally installed native host manifest. The stdio relay never reads a vault file. On Linux it uses a private per-user Unix socket. On Windows the desktop starts a local named-pipe broker restricted to the current user's SID and session. The broker refuses remote clients and a preexisting pipe name, and the relay verifies the broker’s account and session. The broker exits with the desktop. The Windows package hardens Electron’s ASAR loading and checks embedded archive integrity, which does not replace Authenticode signing. The user opens the real popup and selects an exact HTTPS match. Fill stays bound to the original top-frame document, checks origin and form targets again, declines conflicts, and does not submit. Browsers and pages receiving a filled password can read it. Active same-user malware and a compromised Chrome or same-origin site are outside the trust model.
