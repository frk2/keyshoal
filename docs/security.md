# Security design, version 1

Keyshoal protects a closed vault copied from disk and authenticates devices on an untrusted LAN. It cannot protect secrets from a compromised operating system, browser, or unlocked app. It is not independently audited. Use a high-entropy passphrase and keep a separate backup of the two factors.

## Vault key and binary format

- System CSPRNG on first desktop setup generates a 32-byte security key, a 16-byte public vault ID and a 16-byte public salt. Desktop does not save the security key. iOS stores the paired key and the LAN credential in this phone’s `WHEN_UNLOCKED_THIS_DEVICE_ONLY` Keychain. Neither platform saves the passphrase.
- Compute `HMAC-SHA-256(key=security key, message=exact UTF-8 passphrase)`. Stretch that with Argon2id v1.3 at 64 MiB, 3 passes, 4 lanes and a 32-byte result. The cost is fixed for format v1, so an untrusted header cannot request arbitrary memory. Separate 32-byte keys are expanded by HKDF-SHA-256, using the vault ID as salt and `keyshoal/v1/{catalogue,password,file,enrol}` as distinct info values.
- Each 128-bit random login ID names two independent XChaCha20-Poly1305 boxes. Each box begins with a fresh random 24-byte nonce, then ciphertext and its 16-byte tag. AAD is `keyshoal/v1/catalogue` or `keyshoal/v1/password` followed by the binary vault ID and login ID. The catalogue JSON contains the title, canonical website origin and username. The password box is a separate JSON string.
- File layout in unsigned big-endian order is ASCII `KSHOAL01`, 16-byte vault ID, 16-byte salt, 4-byte entry count, sorted entries, then a 32-byte HMAC-SHA-256 over everything preceding the tag. An entry is its 16-byte ID, 4-byte catalogue-box length, 4-byte password-box length, and those two boxes. IDs must be strictly increasing. File, record and box sizes are bounded before parsing. The file MAC is verified before parsing the entry list. Unknown or damaged formats fail closed.
- After unlock, listing only opens catalogue boxes. A password box opens only on explicit reveal, edit, copy or the selected exact-origin Chrome fill. Sync, merge and integrity checks operate on ciphertext and do not decrypt password boxes. The Electron main process holds the active vault and sends only needed values to its sandboxed renderer. Save uses an atomic replacement of a private 0600 Linux file in an owned 0700 directory. iOS uses a protected, atomic file excluded from backups, holding both local and last-synced ciphertext.
- Desktop locks after five minutes of inactivity, on suspend, and on screen-lock events where Electron supplies them. iOS locks when leaving the foreground and after five minutes without activity. Key bytes are wiped on a best-effort basis. Managed runtimes do not guarantee string or heap zeroization. Reveal hides after 20 seconds. Desktop copy clears the unchanged current clipboard after 30 seconds. iOS copies to a local-only pasteboard item expiring after 30 seconds. OS clipboard managers, accessibility and screenshots are separate trust boundaries.

Cryptographic primitives come from [noble-hashes](https://github.com/paulmillr/noble-hashes) and [noble-ciphers](https://github.com/paulmillr/noble-ciphers). The Argon2id parameters match the memory-constrained profile in [RFC 9106](https://www.rfc-editor.org/rfc/rfc9106#section-4).

## QR, authentication, and sync

The desktop is the sync hub. Its listener is off by default, binds only a user-selected active RFC 1918 IPv4 address on TCP 46321, and shuts down on lock. No discovery, relays, automatic port forwarding, analytics, or cloud account. A self-signed ECDSA P-256 certificate has an IP subject alternative name. The desktop persists its certificate and TLS private key in a separate local 0600 file. Keys/certificates are renewed on address change or approaching expiry.

The in-app QR contains the private address, the SHA-256 fingerprint of the certificate DER, the security key, and one random 256-bit invite. The QR is secret, is valid for at most two minutes and is consumed on successful enrolment. The iOS sync module will not follow redirects, uses an ephemeral session, and accepts only the pinned certificate with the configured private address. Transport uses TLS 1.3. No user-installed CA or blanket certificate bypass is needed.

- `GET /v1/vault` with `Authorization: Invite <token>` returns the current binary snapshot so the client can unlock it locally. A copied QR thus exposes both the security key and temporary access to ciphertext, but not the passphrase.
- `POST /v1/enrol` with the invite and `X-Keyshoal-Proof` (hex HMAC of the context `keyshoal/v1/invite proof` plus the binary invite, under the derived enrol key) demonstrates the two factors without sending the passphrase. The server consumes the invite and issues a distinct, revocable 256-bit device token. The desktop only stores its hash. Each paired device credential is a bearer secret.
- `GET /v1/vault` with `Authorization: Device <token>` returns the current binary snapshot. The client checks the file MAC and vault identity. The client three-way merges local, last synced and current desktop states by encrypted record. Absence relative to the base describes deletion. Independent changes merge, including concurrent adds. It stops for a decision on overlapping edits or edit versus delete. Consent to resolve a conflict applies to the specific reviewed desktop revision only.
- `PUT /v1/vault` sends the merged authenticated binary snapshot, with the SHA-256 revision of the fetched snapshot in `If-Match`. The desktop rechecks auth on completion, verifies the revision and file MAC, then atomically commits. Stale writers receive 412 and recompute instead of silently overwriting. Desktop edit/delete also checks the encrypted record stamp when a phone synced during editing. These are full snapshots, not byte-level deltas.

Any enrolled device with the two vault factors can author changes. Revoking its sync credential does not revoke its offline data or erase secrets it already knows. To recover from disclosure of both factors, create a new vault and rotate the affected website passwords. Key rotation and rollback detection for an attacker who can replace local files with an old authentic snapshot are not implemented. File creation time, sizes, record count, random IDs, connections and traffic volume may be observable. The listener does not guarantee availability against malicious local peers or router/client isolation.

## Chrome boundary

The Manifest V3 extension has `activeTab`, `scripting` and `nativeMessaging`, no broad host permission, content script or background password cache. The user invokes the popup and selects a login. Chrome permits only the extension ID installed in the Native Messaging host manifest. The small stdio host relays a bounded request over an owned per-user Unix socket, never reads the vault file, and does not log messages. The desktop offers only titles matching the active HTTPS origin and releases one password for an explicit matching fill. The script targets the original top-frame document ID, checks its origin again, declines unsafe/ambiguous forms, and leaves submission to the user. Normal browser privileges allow the receiving site to read a filled password. A malicious process already running as the same OS user, a malicious site on the *same* origin, or compromised Chrome/extension is out of scope.
