# Windows handoff

No Windows binary was built on Linux. Keep the web extension, vault bytes and LAN protocol compatible. Work with a new branch and synthetic data on Windows 11, then review in a separate pull request.

1. Install Node 22.22+ and the Windows build tools. Run `npm ci`, `npm exec -- install-electron`, `npm test`, and `npm run build:desktop`. Start the bundled desktop with `npm start`. Do not reuse a production vault for testing. The shared Electron main code and LAN hub are platform-neutral apart from the native Chrome bridge and filesystem permission handling.
2. Implement a Windows named-pipe bridge alongside the Unix implementation in `desktop/bridge.js`. Restrict the pipe to the interactive user's SID, reject remote clients, and reject another process pre-creating the name. Do not rely only on a random pipe name or the default DACL. If Node’s pipe server cannot set the ACL and `PIPE_REJECT_REMOTE_CLIENTS`, use a small audited Windows helper/addon to create it. Preserve the 4-byte little-endian framing, bounded messages, exact-origin checks and desktop lock requirement. Validate the private vault directory and all TLS/token files with a current-user ACL too. Test atomic writes using real NTFS and ensure failed writes keep the old vault usable.
3. Ship a Windows Native Messaging relay executable. Use binary stdin/stdout mode, bounded native-endian (Windows little-endian) 4-byte framing, read/write loops, and timeouts. Validate the Chrome origin argument, never log request or reply contents, and prevent a launch from making duplicate desktop vault instances. Connect only to the restricted Windows pipe. The Linux C host in `desktop/chrome-host.c` is a framing reference, not directly portable.
4. Register `com.keyshoal.desktop` under `HKCU\Software\Google\Chrome\NativeMessagingHosts\com.keyshoal.desktop`. Set the default value to the absolute path of a Chrome host JSON manifest. Include `name`, `description`, absolute executable `path`, `type: stdio`, and the exact installed extension’s `chrome-extension://EXTENSION_ID/` in `allowed_origins`. Add a matching uninstall step. Verify [Google’s Chrome Native Messaging documentation](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging) for registration details.
5. Extend `scripts/package.mjs` or use equivalent Electron tooling for Windows x64, preserving the security fuses and ASAR. Enable embedded ASAR integrity validation if the packaging tool can provide the required integrity metadata. Provide a portable zip or per-user installer. Treat Authenticode code signing and browser-store registration as later, explicitly authorized publishing steps. Never add a global firewall rule. Verify normal Windows firewall behavior when the user starts sync on their private LAN.
6. Test a signed or unsigned build in a clean Windows profile as appropriate. Verify create/reopen, wrong key, encrypted storage, exact-origin fill, locked bridge, Chromium profile isolation, malicious different-user pipe clients denied, stale writes, and sync on a second device. Transfer only deliberately synthesized test data between Linux and Windows to prove interoperability. Document anything still unverified.
